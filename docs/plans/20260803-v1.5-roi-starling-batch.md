# L10n TM Companion 1.5 ROI 与 Starling 批量能力计划

## 目标

本轮以用户提供的 `l10n-tm-companion#7.zip` 1.4.0 为候选来源，将可验证的 OAuth Broker 与异步 ROI 原型受控导入权威项目目录，同时保留当前项目已经实现的自动全语言 ROI、RWS/Pactera 共用 TM snapshot、延后 scope 只计算 A/C 的请求优化和 Inspire Prompt 精简。最终插件、Backend、文档、安装包与 Git 分支统一为 1.5.0。

## 业务边界

- 正式 ROI 始终是 `TM Cost(A) - TM Cost(C)`，B 只用于首屏 AI 审阅证据。
- ROI 开启后自动覆盖已选项目共同支持的非英语 target locale，不要求 CD 选择 vendor 或语言；RWS 与 Pactera 从同一套 A/B/C TM snapshot 分别派生金额。
- 当前展示 scope 保持同步完成 Final TM 与 Working Sheet 写入；延后语言只查询正式金额所需的 A/C，不重复执行 B。
- Broker 与 Worker 代码可以进入 1.5.0，但生产 feature flag 在公司网关、身份、Secret Manager/KMS、Feishu、Starling 和 ROI_Test 门禁完成前保持关闭。
- Starling 40 条额度在 RD 正式确认和 PPE 验证前不得作为已生效能力。1.5.0 提供明确的批大小配置与上限校验，默认继续使用已验证的 10 条。

## 实施切片

1. 固定并验证当前主目录与 ZIP 1.4.0 基线，记录 ZIP hash、版本、测试和候选边界。
2. 在隔离 worktree 中将 ZIP 1.4.0 转换为可审计的 Git 导入提交，只导入新增或修改文件，不删除当前项目资产。
3. 在 `codex/publish-v1.5.0` 合并候选提交，逐个解决共享文件冲突：ROI、Prompt、UI 与当前项目契约优先；Broker 路由、Backend、Native Host 和门禁测试按候选实现导入。
4. 用测试驱动增加 Starling source batch capability：默认 10，显式配置可提高到 40；project IDs 继续固定最多 10；非法值正确失败。
5. 将插件 manifest、Backend package、README、用户指南、安装手册、Popup 配置、E2E Checklist 和长期 ROI/TM 文档增量同步到 1.5.0。
6. 运行全部 JavaScript、Python、Backend、语法、OpenAPI、安装器 contract、构建与凭证扫描，实际检查日志和安装包内容。
7. 逐文件暂存、提交、普通 push 到 GitHub 的 `codex/publish-v1.5.0` 分支，并记录 commit、远端、安装包 hash 与仍未完成的真实集成门禁。

## 验收证据

- 自动 ROI 行为、双 vendor payload、Items 去重、A/C 请求边界和 50–85 AI 门禁有回归测试。
- 10 条默认和 40 条显式能力均有 public-interface 测试，超过已配置上限正确失败，响应顺序保持稳定。
- Broker 关闭时不改变现有客户端功能；Broker 开启时不静默回退本机 Secret 或同步归档。
- 全量插件与 Native Host 测试零失败；Backend 本地 contract 测试零失败；安装包版本和源码一致。
- GitHub 远端分支指向本轮已验证 commit，不使用强推，不覆盖 `main`。

## 未纳入完成声明的事项

公司 Backend 部署、无 Secret 新 Mac 的真实 Feishu OAuth、真实 ROI_Test 三表归档、Starling 40 条额度、40 条 payload 的顺序与完整性、3/6 并发 P95、Pilot 和 Production 均需要外部系统证据；本轮只会报告实际获得的证据。
