## 一、一句话

Chrome MV3 扩展：从表格读英文原文 → 查 Starling TM 记忆库 → AI 改写原文提升 TM 命中率 → 算匹配度 → 写回表格。纯客户端，无后端，全程在用户本机跑。

## 二、技术路线（怎么实现的）

### 2.1 核心数据流

```
输入源（飞书电子表格 A 列原文）
   ↓
① 读原文（飞书 Sheets API，tenant_access_token 鉴权）
   ↓
② 查 TM：原文 → background.js（Service Worker）
        → Native Messaging → 本地 Python 脚本 starling-bridge.py
        → 调用本机 starling-cli → Starling TM 服务
        → 返回 {TM译文, TM库原文, 相似度 Orig%}
   ↓
③ AI 改写：对 Orig% < 75 的条目，AI 改写英文原文让它更贴近 TM 已有原文
        （同样走 background → Python 桥接 → LLMBox 网关，绕过浏览器 CORS）
   ↓
④ 算 New Match%：文本相似度算法（Jaccard + Levenshtein）
        算「改写后原文 vs TM 库原文」
   ↓
⑤ 对比生成 Comment（improved / different / same / no_tm）
   ↓
⑥ 写回表格 B-H 列（按真实行号定位，不错位）
```

### 2.2 架构决策

| 组件 | 选择 | 为什么 |
|------|------|--------|
| 后端 | ❌ 无，纯客户端 | TM 数据敏感留本地；内部工具不需运维 |
| 扩展标准 | MV3 | MV2 已停用 |
| TM 查询 | Native Messaging 调本机 CLI | 浏览器唯一能调本地程序的方式；starling-cli 是字节内部工具只能本机跑 |
| LLM 调用 | 走 Native Messaging → Python 直连 LLMBox | 浏览器直连 LLMBox 撞 CORS（已踩坑修复），Python 直连无此限制 |
| 表格 | 飞书电子表格 Sheets | 团队实际用 Sheets |
| 鉴权 | tenant_access_token | 飞书应用已发布 |
| 前端 | 原生 JS（无框架） | UI 简单，避免构建链 |

### 2.3 三个本机依赖（限制分发）

给别人用前，对方机器必须装齐，否则 TM/LLM 功能不可用：
1. `starling-cli` + AK/SK（`~/.starling-cli/.starlingrc.json`）
2. Python 桥接脚本 `starling-bridge.py`
3. Native Messaging Host 注册到 Chrome（`~/Library/Application Support/Google/Chrome/NativeMessagingHosts/`，allowed_origins 绑扩展 ID）

### 3.2.1 诊断方法论（下次排查 native host 问题照搬）

Chrome 调 native host 的报错（"communicating with native messaging host" / "No TM match" / 偶发失败）难定位，因为 Chrome 启的子进程环境与终端不同，崩溃信息无处可看。已在 `starling-bridge.py` 内置诊断：

- **`/tmp/l10n-bridge-debug.log`**：bridge 每次启动记录 PATH / `which starling-cli` / python / 收到的 action；handler 崩溃记 `HANDLER CRASH` + 完整堆栈
- 排查步骤：`rm -f /tmp/l10n-bridge-debug.log` → 刷新扩展 → 触发流程 → `cat /tmp/l10n-bridge-debug.log`
- 关键看：PATH 是否极简（Chrome 默认 `/usr/bin:/bin:/usr/sbin:/sbin`）、`which starling-cli` 是否 None、有无 CRASH

## 六、关键经验（避免重复踩坑）

1. **popup 调 native host 必须经 SW 中转**：`sendNativeMessage` 只在 background SW 可用。判断扩展环境用 `chrome.runtime?.sendMessage`，不是 `sendNativeMessage`。
2. **MV3 promise 形式错误走 reject**：`await chrome.runtime.sendMessage(...)` 错误时 reject，不是设 `lastError`，用 `.catch` 捕获。
3. **MV3 SW 会休眠**："Service Worker（无效）"多半是空闲休眠，不是崩溃，收到消息自动唤醒。
4. **Chrome 扩展 JS 有缓存**：改了代码刷新扩展有时不生效，需关掉开关再开，或移除后重新加载已解压目录。
5. **glm-5.2 响应有 thinking 块**：`content` 数组第一个是 thinking（无 text），真实文本在 `type=='text'` 块，需遍历。
6. **Sheets 读 A 列跳空行要保留真实行号**：写回时按 row 定位，否则错位。
7. **Chrome 启 native host 子进程的 PATH 极简**：只有 `/usr/bin:/bin:/usr/sbin:/sbin`，终端能找到的 starling-cli/node 在 Chrome 环境找不到 → 调用静默失败被当成"无匹配"。bridge 必须 `_augment_path()` 主动补 node 目录 + `resolve_cli` 探测候选绝对路径。
8. **native host 排查看 `/tmp/l10n-bridge-debug.log`**：bridge 内置诊断日志，记 PATH/which/收到的 action/崩溃堆栈。排查步骤：清日志→刷新扩展→触发→cat 日志。
9. **MV3 SW 空闲休眠**：首条消息可能撞 SW 未唤醒导致 "communicating with native messaging host" 报错（偶发），刷新扩展重新唤醒可解；bridge main 应全局捕获 `BrokenPipeError` 等不挂。
